## 記録フォーマット

```
## ADR-XXX: タイトル
- **日付**：YYYY-MM-DD
- **状態**：提案中 / 採用 / 却下 / 廃止
- **背景**：なぜこの判断が必要だったか
- **決定内容**：何を選んだか
- **却下した選択肢**：何を選ばなかったか・理由
- **影響**：この決定による制約・副作用
```

## ADR-002: コンボボックス CBN_CLOSEUP でフォーカス再設定を必須化／WM_ACTIVATE で DefWindowProc を呼ばない

- **日付**：2026-06-23
- **状態**：採用
- **背景**：プレビュータブのコンボでMDファイルを切り替えた後、エクスプローラから別ファイルを開く等で他アプリをアクティブにしてからダイアログに戻ると、ウィンドウが見えなくなり一切反応しなくなる不具合が発生した。デバッガで中断するとメインスレッドが `CDialogEx::OnActivate` → MFC内部 → `user32.dll` 内に滞留しており戻ってこない状態だった。原因は、コンボのドロップダウンリストボックスが破棄された後も Windows のフォーカス履歴に破棄済みリストボックスの HWND が残り、後の `WM_ACTIVATE` 処理で `DefWindowProc` がそのデッドハンドルへ同期 `SendMessage` を発射して応答待ちになるため。
- **決定内容**：
  1. ドロップダウン破棄ハンドラ（`CBN_CLOSEUP`）で `ReleaseCapture` と有効な HWND への `SetFocus` を必ず行い、フォーカス／キャプチャ履歴をクリーンに保つ。
  2. `WM_ACTIVATE` ハンドラからは基底クラス（`CDialogEx::OnActivate`）を呼ばず、`DefWindowProc(WM_ACTIVATE)` 経路を完全に経由させない。タイトルバー再描画は `WM_NCACTIVATE`（別メッセージ）で処理されるため視覚的実害はない。
- **却下した選択肢**：
  - `SetForegroundWindow` / `AttachThreadInput` 等の「強制フォアグラウンド」トリック → `WM_ACTIVATE` の再帰発火でメッセージポンプが破綻、本丸のデッドハンドル参照は解消しない。
  - `CBN_SELCHANGE` → `CBN_CLOSEUP` への切替や `PostMessage` での遅延 → 同期競合の緩和にはなるが、フォーカス履歴に残るデッドハンドルは消えないため不十分。
  - `RDW_UPDATENOW` 除去等の同期再描画削減 → 描画ではなく `SendMessage` 応答待ちが真因のため効果なし。
- **影響**：今後ドロップダウン系コントロール（コンボ・リストボックス等）を導入する際は同パターン（破棄ハンドラでフォーカス再設定）を必ず適用する。アクティベート系の不具合に直面したら、まずフォーカス／キャプチャ履歴を疑い、強制フォアグラウンド系の対策には手を出さない。
